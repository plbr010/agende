## Ensaio no staging (`agende-staging`, `fkpdudnnperufnmdwdlv`) — concluído

1. Primeira tentativa falhou atomicamente com `workspace_subscription_inactive`: um backfill toca linhas de salões com assinatura expirada. **Produção falharia igual** (todas as assinaturas expiradas). Os ensaios locais anteriores não pegavam isso porque usavam só salões com direito ativo.
2. A correção fica no pacote, não nas migrations (hashes inalterados): `set_config('app.bypass_entitlement','on',true)` só na transação. Esse interruptor pula apenas o gatilho de direito; o gate de criação de agendamento o ignora explicitamente.
3. Segunda tentativa: aplicada. Contagens preservadas (47 salões, 75 agendamentos, 37 lançamentos, 47 assinaturas), 10 recibos de abertura criados, ledger com as versões, todas as tabelas `public`/`app` com RLS + FORCE (exceto `app.stripe_checkout_leases`, igual à produção e fora da API).
4. `admin_salon_read_model` aplicada em seguida. Sonda em transação abortada: as 14 RPCs master retornam JSON para a identidade master; para um usuário confirmado comum, todas as checadas devolvem `not_platform_admin`.
5. `select app.resume_booking_creation();` executado no staging: criação de agendamento reaberta.
6. Advisors de segurança do Supabase: nenhum `ERROR` em staging nem produção. Recomendado ativar "Leaked password protection" no Auth (configuração de produção — decisão do proprietário).

## Aplicação em produção — exige aprovação explícita do proprietário

Pré-condições:

1. Backup: confirmar o backup diário do Supabase de hoje (ou PITR) e exportar `public.financial_entries`, `public.appointments`, `public.subscriptions` por SELECT antes da janela.
2. Gerar o pacote no SHA aprovado: `node scripts/build-production-rollout.mjs rollout.sql` (verifica hashes; aborta se algum divergir).
3. Ensaio na própria janela, sem efeito: `node scripts/build-production-rollout.mjs dry.sql --rollback` e executar `dry.sql`. Termina em `ROLLBACK`.

Aplicação:

```bash
npx supabase@latest db query --remote=wohimauqgywshbbejjcl -f rollout.sql
```

A transação aborta sozinha se qualquer versão já existir no ledger (`rollout_precondition`) ou se qualquer instrução falhar. Nada fica pela metade.

Decisão separada (comercial): o pilot gate deixa a criação de agendamentos **fechada para todos**. Para vender, após a aplicação:

```sql
select app.resume_booking_creation();
```

Reverter a qualquer momento com `select app.suspend_booking_creation();`. Cada salão continua precisando de trial/assinatura/cortesia ativa.

Pós-verificação: os SELECTs de `docs/production-readiness/rollout-20261109-verify.sql`.

## Reversão

- Falha antes do COMMIT: nada a fazer, rollback integral.
- Depois do COMMIT: não usar DROP CASCADE. As migrations de comissão criam ledger financeiro; reverter = restaurar backup em ambiente isolado e conciliar. Para o painel master, as RPCs são só leitura e podem ser removidas individualmente (ver `admin-rpc-restoration-20261106.md`).
- O frontend publicado já depende destas RPCs; reverter o banco sem reverter o frontend volta ao estado quebrado atual.
