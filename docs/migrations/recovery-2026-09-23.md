Inspeção somente leitura do catálogo (`pg_proc`, `pg_trigger`) e do histórico:

  workspace, serviço ativo e vínculo de serviço. Essa lógica já aparece na
  migration anterior `20260918195354_agenda_snapshot_professional_and_select`.
- `app.product_timezone` retorna `America/Sao_Paulo`, já definido em
  `20260918194355_agenda_functions`.

  fuso do produto como fallback. Existe definição anterior no Git, em
  `20260918203839_public_booking_schema`.

  e o constraint trigger `workspace_members_keep_owner`. A função protege
  o último owner ativo e usa lock de membership. Esses objetos não aparecem
  com esses nomes nas 54 migrations locais. O Git já tinha proteção de último
  owner em RPCs de `20260918194427_workspace_settings_rpcs`, o que não prova
  equivalência com esse trigger.
- A migration imediatamente anterior é `20260918203841_public_booking_rpcs_rls`;
  a seguinte é `20260919201409_inventory_schema`, cujo SQL se declara isolado
  de agenda, timezone e owner. As posteriores usam `workspace_timezone`, mas
  não recuperam o SQL perdido.
- Os três registros remotos `20260918203839`, `20260918203840` e
  `20260918203841` contêm apenas `-- applied via execute_sql`.
  Seus arquivos SQL existentes no Git foram preservados integralmente:
  esses comentários remotos não substituem o SQL já versionado.

## Método e limites

Apenas SELECTs foram executados no remoto. Nenhuma migration, DDL, escrita,
repair, db push ou db reset foi executado. Não houve replay local das
migrations; a validação desta recuperação é de proveniência, integridade
do SQL e comparação de versões/nomes, não de execução em banco vazio.

Consulta de conferência:

```sql
select version, name, cardinality(statements) as statement_count,
       md5(array_to_string(statements, E'\n')) as sql_md5
from supabase_migrations.schema_migrations
order by version;
```

A contagem de drift compara o par versão/nome, não os hashes das migrations
preexistentes. Os hashes das 23 recuperadas foram verificados individualmente.
